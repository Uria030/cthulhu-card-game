## 二、資料組成(DB 表)

| 表 | 內容 | 量 |
|---|---|---|
| `talent_trees` | 每陣營 1 棵,含 description_zh / design_notes / primary·secondary_attribute / combat_proficiency | 8 |
| `talent_branches` | 每棵 3 條分支(含 theme / color_hex / 機制 / Ultimate 結構 design_notes) | 24 |
| `talent_nodes` | 每棵 32 節點(trunk 2 + 三分支各 10) | 256 |
| `talent_node_effects` | 各節點 1-3 條 effect(effect_code / params / desc / **effect_value**) | — |
| `card_definitions`(軸內卡) | 各樹 15-21 張,帶 `talent_branch_lock`(格式 `<陣營>_<分支>` 如 `E_1`) | — |

**節點結構(每棵 32):** Lv1-2 共通主幹(passive + attribute_boost)→ Lv3 三選一(branch_choice)→ Lv4 passive / Lv5 **proficiency** / Lv6 **milestone(質變)**→ Lv7 boost / Lv8 prof / Lv9 **talent_card** → Lv10 boost / Lv11 passive / Lv12 **ultimate**。

**V 值預算(Uria 鎖定硬約束):** 整樹 **328V** / 單分支 **106V** / Ultimate **18V**;1 天賦點 ≈ 9.7V;12 級 V 階梯 ±20%。

⚠ **effect_value 注意**:Gemini 不穩定填 effect_value,driver 部分回填;**樹層 V 靠 stage A 的 target_V 把關**(stage C),非加總 effect_value。所以 admin UI 單節點 V 可能顯示偏低/空(實際 V 合計 ~100-170/樹),這是已知現象不是 bug。

## 三、量產 driver(本機,不上 git)

`scripts/mod-agent-local/talent-trees/run-talent-tree.mjs`

```
node ...run-talent-tree.mjs <faction>            # dry-run(不入庫)
node ...run-talent-tree.mjs <faction> --post     # 入庫
node ...run-talent-tree.mjs <faction> --from-cache --post   # 重用 .stage-*.json,不重燒 Gemini
```

**5 階段**:A 整棵架構(1 Gemini call)→ B 三分支內容(3 call)→ C 本機橫向校驗 → D 有趣度自評+撞車檢查(1 call)→ E 入庫(軸卡 POST → tree import → 反查 UUID → 推 prerequisites)。
- 規範主檔:`master_talent_tree.md`。cost ~**$0.35/棵**。idempotent(重跑 skip 既有)。

## 四、使用/設計原則(紅線)

1. **V 階梯**:逐節點 ±20%、三分支兩兩差 ≤5V、整樹 295-360V。
2. **永久卡只能 passive**(規則書 §13b.2);**永久/額外互斥**(§13b.4)。
3. **每分支恰好 1 個卡名軸 + 1 個獨特機制**;軸內卡 `name_zh` 必含該分支軸字串(2-3 字)。
4. **黑名單**(繁中 + 程式術語):禁 tier/boss/精英/血量/理智值/HP/SAN 等(admin-card-prompt §4.3 對照)。
5. **三分支差異化**:機制(計數器/狀態/互動)+ Ultimate 結構(A/B-1/B-2)至少 2 種。

## 五、API 端點

`GET /api/talent-trees`(列表+stats)/ `GET /api/talent-trees/:faction/nodes` / `POST /api/talent-trees/import`(整棵)/ `GET /export` / `GET /compare`。
(注:沒有逐節點 CRUD 端點,整棵走 import。)
