# 生產線操作手冊 — 給任何 AI 操作員(含低階模型/Codex)

> **用途**:任何 AI 操作員照本手冊即可啟動與監看 Gemini 量產線。本手冊刻意寫成「照步驟做,不需要判斷力」——所有需要判斷的地方都寫死了「停手上報」。
> **版本**:v0.1|**日期碼**:26070205
> **體制**:《生產線Agent計畫_v0_1_26070204》(兩個 Agent 定義 × N 份派工單)+《品管三層制_v0_1_26070203》

---

## 第 0 節|操作員守則(先讀,違反即事故)

你**可以**:跑本手冊列出的指令、讀檔案、監看進度、回報。
你**絕不**:
1. 自己寫任何遊戲內容(卡片/背景/名字/敘事)——內容只能由 driver 內的 Gemini 產。
2. 手改 Gemini 產出後入庫。
3. 跳過或關閉 validator。
4. 修改 driver / master file / 規範文件(那是 Claude 主 session 品質主管的工作)。
5. 對「手冊沒寫的狀況」自行決定——一律停手,照第 5 節上報。

工作目錄:`C:\Ug\cthulhu-card-game`

```bash
# 1. admin token 是否有效(過期會回 Invalid or expired token)
node -e "const fs=require('fs');fetch('https://server-production-fc4f.up.railway.app/api/admin/investigators?limit=1',{headers:{Authorization:'Bearer '+fs.readFileSync('.g1-token','utf8').trim()}}).then(r=>r.json()).then(j=>console.log(j.error??'token OK'))"

# 2. token 失效 → 刷新(憑證檔 g1-cred.txt 需存在;不存在 → 停手上報)
node scripts/g1-sandbox/read-cred-and-login.mjs

# 3. Gemini 鑰匙存在
ls GeminiKey.txt
```

三項任一失敗且無法照上面修復 → 停手,照第 5 節上報。

## 第 2 節|標準流程 A:透過 Claude Code 派 Agent(建議,判斷力外包給 Agent)

適用:機器上裝有 Claude Code CLI。Agent 定義在 `C:\Ug\.claude\agents\`(production-runner / qc-production)。

```bash
# 啟動生產(把 MOD-XX 換成目標線;派工單路徑見第 6 節)
claude -p "以 production-runner agent 執行派工單 docs/production_orders/MOD-11_派工單.md,批次清單:<代碼逗號分隔>。完成後輸出 batch-report 路徑。" --permission-mode acceptEdits

# 啟動品管(另開一個終端,同時跑)
claude -p "以 qc-production agent 監工派工單 docs/production_orders/MOD-11_派工單.md 的當前批次,每入庫 2 位抽 1 位,停線事件與 QC 報告寫到 scripts/mod-agent-local/investigator-cards/qc-report.md。" --permission-mode acceptEdits
```

之後你的工作只剩:每 10-15 分鐘看一次兩個終端的輸出與 report 檔;出現「停線」字樣 → 照第 5 節上報。

## 第 3 節|標準流程 B:直接跑 driver(無 Claude Code 環境)

適用:Codex 或任何有 shell 的操作員。判斷力由 driver 內建的 validator gate 代替——你只是啟動與監看。

以 MOD-11 為例(其他線見各自派工單):

```bash
cd C:\Ug\cthulhu-card-game
# 批次啟動(代碼清單來自派工單;輸出即時進度與逐位入庫結果)
node scripts/mod-agent-local/investigator-cards/run-batch-investigators.mjs ENFP-1,INFJ-1,ESFJ-2
```

**監看要點**(driver 輸出逐位打印):
- `✅ 入庫` = 正常;`⏭ skip` = 已存在(冪等,正常)
- `gate 重試` = validator 擋下重產中(正常,最多 2 次)
- `❌ error` = 該位三連敗放棄——**不是事故**,記下代碼,批次結束後照第 5 節一併上報
- 成本行:driver 每次呼叫會印累計花費;**超過派工單上限的 92% → 立刻 Ctrl+C 停線上報**

**批次結束後必跑**(結果貼進回報):

```bash
# 逐位驗證(id 用 driver 輸出的;或用清單查詢腳本)
node -e "const fs=require('fs');const H={Authorization:'Bearer '+fs.readFileSync('.g1-token','utf8').trim()};(async()=>{const l=await(await fetch('https://server-production-fc4f.up.railway.app/api/admin/investigators?limit=100',{headers:H})).json();for(const t of l.items.filter(x=>x.title_zh)){const v=await(await fetch(`https://server-production-fc4f.up.railway.app/api/admin/investigators/${t.id}/starting-deck/validate`,{headers:H})).json();const d=v.data??v;console.log(`${t.mbti_code}-${t.career_index} ${d.isValid?'OK':'FAIL '+JSON.stringify(d.errors)}`)}})()"
```

## 第 4 節|多 Agent 並行增產

- 同一條線開 2 個以上生產程序:**清單切段,絕不重疊**(例:44 位切 22+22,兩個終端各跑一段)。
- 不同線並行:無限制(寫不同資料表)。
- 並行時成本上限按「全部程序加總」計——每個終端各自記,總和逼近上限就全停。

## 第 5 節|停手上報規則(唯一的判斷 = 不判斷)

遇到以下任何一種,停手、收集資訊、上報給 Uria 或 Claude 主 session,**不要自己修**:

| 狀況 | 上報附帶 |
|---|---|
| error 三連敗的單位 | 代碼+driver 印出的違規原因 |
| 成本逼近上限 | 累計金額+剩餘清單 |
| driver 崩潰/API 5xx 連續 3 次 | 最後 30 行輸出 |
| 手冊沒寫的任何狀況 | 你看到什麼+你當時在跑什麼 |
| 產出看起來怪(即使 validator 放行) | 代碼+哪裡怪——**寧可誤報** |

上報格式:`【上報】一句話狀況 | 批次/代碼 | 證據 | 我已停在哪一步`
